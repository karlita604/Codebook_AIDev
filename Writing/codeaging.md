# Tracking Code Age, Modification Count, and Review Count at Method/Class Granularity in GitHub Repositories: An Annotated Literature Guide

## TL;DR
- For fine-grained (method/class-level) history tracking on GitHub, the state of the art is **CodeTracker / CodeTracker 2.0** (Jodavi & Tsantalis, FSE 2022; Hasan et al., TSE 2024) — refactoring-aware via RefactoringMiner, reporting 99.9% precision and recall in method tracking; **CodeShovel** (Grund et al., ICSE 2021) is the most practical lightweight alternative (complete change histories for 90% of methods, including 97% of all method changes), and **FinerGit / Historage** (Higo 2020; Hata 2011) integrate directly with git.
- The conceptual foundations are **Parnas "Software Aging" (ICSE 1994)**, **Lehman's laws of software evolution (1980)**, and **Eick et al. "Does Code Decay?" (TSE 2001)**; for "how many times code was touched," the key process-metric works are **Nagappan & Ball code churn (ICSE 2005)**, **Hassan change entropy (ICSE 2009)**, **Rahman & Devanbu (ICSE 2013)**, and method-level **Giger et al. (ESEM 2012)**.
- For "how many times code went through review," link commits/PRs to changed regions using **McIntosh et al. review coverage (MSR 2014 / EMSE 2016)**, the **CROP dataset (Paixão et al., MSR 2018)**, and mine PRs via **Gousios pull-based model (ICSE 2014) / GHTorrent (MSR 2013)** — but beware the pitfalls documented in **Kalliamvakou et al. "Promises and Perils" (MSR 2014 / EMSE 2016)**.

## Key Findings
- **Method/class tracking is a solved-enough problem for Java**: refactoring-aware tools (CodeTracker) achieve near-perfect accuracy, but they depend on RefactoringMiner and are largely Java-only. For polyglot GitHub corpora you will need language-specific fallbacks (PyRef for Python, RefDiff for multi-language) or accept git's line-based approximations.
- **Untracked changes are a real threat**: Hora et al. (ICSE 2018) found that between 10 and 21% of method-level changes across 15 large Java systems are "untracked" (renames/moves), resulting in a large proportion (25%) of entities whose histories may be split — this directly biases any "code age" or "number of revisions" metric if you rely on naive `git log`.
- **Process metrics beat static metrics for predicting defects/maintainability**, and "number of prior changes/revisions" and churn are among the strongest signals — relevant if your study relates age/modification count to quality.
- **Review count requires linking review events to code regions**, which git history alone does not provide; GitHub PR data and Gerrit datasets (CROP) are the practical bridges, subject to squash-merge and "PR not marked merged" pitfalls.

## Details

### Theme 1 — Code aging, decay, and laws of software evolution (foundational, most-cited)

- **David L. Parnas, "Software Aging," Proc. 16th International Conference on Software Engineering (ICSE 1994), pp. 279–287.** The seminal conceptual paper; argues programs "age" from (1) failure to adapt to changing needs and (2) the accumulated damage of changes themselves, and prescribes design-for-change, documentation, and reviews to slow decay. Frames *why* code age matters at the level of modules/entities.
- **Meir M. Lehman, "Programs, Life Cycles, and Laws of Software Evolution," Proceedings of the IEEE, 68(9), 1980, pp. 1060–1076** (laws later extended with Belady and in the FEAST work, e.g., Lehman et al., "Metrics and Laws of Software Evolution — The Nineties View," Metrics 1997). Establishes the laws of continuing change and increasing complexity (E-type systems), the theoretical backbone for expecting entities to change repeatedly and complexity to grow unless work is done.
- **Stephen G. Eick, Todd L. Graves, Alan F. Karr, J.S. Marron, Audris Mockus, "Does Code Decay? Assessing the Evidence from Change Management Data," IEEE Transactions on Software Engineering (TSE), 27(1), 2001, pp. 1–12.** Defines "code decay" operationally (code that is harder to change than it should be) and proposes *code decay indices* measured from change history — including number of changes to a file, number of files touched per change, module size, and average age of constituent lines. This is the direct intellectual ancestor of using modification counts and line-age as decay signals.
- **T.L. Graves, A.F. Karr, J.S. Marron, H. Siy, "Predicting Fault Incidence Using Software Change History," IEEE TSE, 26(7), 2000, pp. 653–661.** Shows change history (number and recency of changes, weighted by age) predicts faults better than product size/complexity — foundational for "recently and frequently touched code is riskier."

### Theme 2 — Tracking a specific entity (method/function/class) across history despite renames/moves/refactorings

- **Michael W. Godfrey, Lijie Zou, "Using Origin Analysis to Detect Merging and Splitting of Source Code Entities," IEEE TSE, 31(2), 2005, pp. 166–181.** Origin analysis: the conceptual foundation for tracing an entity's provenance across renames, moves, merges, and splits (implemented in the Beagle tool, studied on PostgreSQL). Essential background for why entity identity is non-trivial.
- **Hideaki Hata, Osamu Mizuno, Tohru Kikuno, "Historage: Fine-Grained Version Control System for Java," Proc. IWPSE-EVOL 2011, pp. 96–100.** Converts a Java git repo into a finer-grained one where each method/constructor/field is a separate file, so methods can be tracked with native git mechanisms (`git log --follow`), including some rename detection. The original "methods-as-files" approach. (See also Hata et al., "Bug Prediction Based on Fine-Grained Module Histories," ICSE 2012, pp. 200–210.)
- **Yoshiki Higo, Shinpei Hayashi, Shinji Kusumoto, "On Tracking Java Methods with Git Mechanisms," Journal of Systems and Software (JSS), 165, 2020, 110571.** Introduces **FinerGit**, improving Historage's trackability for small/renamed/moved methods (max F-measure ~85% vs Historage's ~70%); the tool was applied to 182 open-source projects comprising 1,768K methods in total (arXiv 2003.05336). Practical because output remains git-native.
- **Felix Grund, Shaiful Alam Chowdhury, Nick Bradley, Braxton Hall, Reid Holmes, "CodeShovel: Constructing Method-Level Source Code Histories," Proc. ICSE 2021, pp. 1510–1522** (ACM SIGSOFT Distinguished Paper). On-demand method-history tool using lightweight string-similarity matching (75% threshold). Per the abstract, it "quickly produces complete and accurate change histories for 90% methods (including 97% of all method changes) outperforming leading tools from both research (e.g., FinerGit) and practice (e.g., IntelliJ / git log)"; validated with a 42-developer survey, a 200-Java-method oracle, and a 16-developer industrial field study. The most usable off-the-shelf option when you don't want repository preprocessing.
- **Mehran Jodavi, Nikolaos Tsantalis, "Accurate Method and Variable Tracking in Commit History," Proc. ESEC/FSE 2022, pp. 183–195.** Introduces **CodeTracker**, the first fully refactoring-aware tracker (built on RefactoringMiner). Per the abstract, it "has 99.9% precision and recall in method tracking, surpassing the previous state-of-the-art tool, CodeShovel," and is "the first tool of its kind that can track the change history of variables with 99.7% precision and 99.8% recall." Corrects mismatches CodeShovel makes on Extract Method refactorings.
- **Mohammed Tayeeb Hasan, Nikolaos Tsantalis, Pouria Alikhanifard, "Refactoring-aware Block Tracking in Commit History," IEEE TSE, 2024 (DOI 10.1109/TSE.2024.3484586; arXiv 2409.16185).** CodeTracker 2.0, extending refactoring-aware tracking to arbitrary code blocks. Evaluated on a manually validated oracle of 1,280 code blocks within 200 methods from 20 open-source Java projects, it reports an overall precision of 99.79% and recall of 99.77% (in ~3.6s on average), versus a GumTree 3.0 baseline's 94.55% precision.
- **Jean-Rémy Falleri, Floréal Morandat, Xavier Blanc, Matias Martinez, Martin Monperrus, "Fine-grained and Accurate Source Code Differencing," Proc. ASE 2014, pp. 313–324.** **GumTree**: the standard AST-differencing algorithm producing edit scripts on ASTs (thresholds minHeight=2, minDice=0.5). The building block underneath many trackers/refactoring detectors. Recent scaling improvements: Falleri & Martinez, "Fine-grained, accurate and scalable source differencing," ICSE 2024; and Martinez, Falleri, Monperrus, "Hyperparameter Optimization for AST Differencing," IEEE TSE 49(10), 2023, pp. 4814–4828.
- **Andre Hora, Danilo Silva, Romain Robbes, Marco Tulio Valente, "Assessing the Threat of Untracked Changes in Software Evolution," Proc. ICSE 2018, pp. 1102–1113.** Per the abstract: "between 10 and 21% of changes at the method level in 15 large Java systems are untracked. This results in a large proportion (25%) of entities that may have their histories split by these changes, and a measurable effect on at least two MSR approaches." The key motivation for using refactoring-aware tracking rather than naive git.
- **RAT: A Refactoring-Aware Tool for Tracking Code History (ICSE 2024 Companion, DOI 10.1145/3639478.3640047)** and **HistoryFinder (arXiv 2507.14716, 2025)** are recent tools extending/critiquing CodeShovel/CodeTracker (e.g., handling merge commits, Javadoc, formatting); useful to cite as the current frontier.

### Theme 3 — Metrics for how many times code was touched/modified (churn, change frequency, fine-grained change extraction, hotspots)

- **Nachiappan Nagappan, Thomas Ball, "Use of Relative Code Churn Measures to Predict System Defect Density," Proc. ICSE 2005, pp. 284–292.** Canonical churn paper: *relative* churn measures (churn normalized by size/temporal extent) strongly predict defect density (Windows Server 2003 case study), while absolute churn is a poor predictor. Directly relevant for normalizing "number of modifications" by entity size.
- **Beat Fluri, Michael Würsch, Martin Pinzger, Harald C. Gall, "Change Distilling: Tree Differencing for Fine-Grained Source Code Change Extraction," IEEE TSE, 33(11), 2007, pp. 725–743.** **ChangeDistiller**: AST tree-differencing that extracts and classifies fine-grained change types (per a source-change taxonomy), letting you count *what kind* and *how many* semantic changes hit a method — richer than line churn.
- **Ahmed E. Hassan, "Predicting Faults Using the Complexity of Code Changes," Proc. ICSE 2009, pp. 78–88.** Introduces entropy-of-changes (Shannon entropy of the change process) as a "code change complexity" metric that predicts faults better than prior-modifications or prior-faults counts. Useful if you want a principled measure of *how spread out / chaotic* the modification history of an entity is.
- **Emanuel Giger, Marco D'Ambros, Martin Pinzger, Harald C. Gall, "Method-Level Bug Prediction," Proc. ESEM 2012, pp. 171–180 (DOI 10.1145/2372251.2372285).** Builds defect prediction at *method* granularity and finds change metrics (fine-grained change history) substantially outperform static source-code metrics for bug-prone methods — the closest direct precedent for method-level modification-count analysis. (Companion: Giger, Pinzger, Gall, "Comparing Fine-Grained Source Code Changes and Code Churn for Bug Prediction," MSR 2011, pp. 83–92 — note this earlier paper has only three authors and compares changes vs. churn.)
- **Foyzur Rahman, Premkumar Devanbu, "How, and Why, Process Metrics Are Better," Proc. ICSE 2013, pp. 432–441.** Per the abstract, the authors "build many prediction models across 85 releases of 12 large open source projects" and find "code metrics, despite widespread use in the defect prediction literature, are generally less useful than process metrics for prediction" — code metrics "stagnate" (repeatedly flag the same files). Strong justification for building your study around change/modification counts. (See also Rahman & Devanbu, "Ownership, Experience and Defects: A Fine-Grained Study of Authorship," ICSE 2011, pp. 491–500.)
- **Thomas Zimmermann, Peter Weißgerber, Stephan Diehl, Andreas Zeller, "Mining Version Histories to Guide Software Changes," Proc. ICSE 2004, pp. 563–572 (extended: IEEE TSE 31(6), 2005, pp. 429–445).** The **ROSE** approach: association-rule mining over version histories to detect *evolutionary coupling* ("entities that changed together"). Relevant for co-change/hotspot analysis at entity level. (A 20-year retrospective appeared in IEEE TSE 51(3), 2025, pp. 842–847.)
- **R. Moser, W. Pedrycz, G. Succi, "A Comparative Analysis of the Efficiency of Change Metrics and Static Code Attributes for Defect Prediction," Proc. ICSE 2008, pp. 181–190.** Early, widely cited evidence (Eclipse) that change metrics outperform static attributes — corroborates Rahman & Devanbu.

### Theme 4 — How many times code went through review (linking commits/methods to PRs and review data)

- **Alberto Bacchelli, Christian Bird, "Expectations, Outcomes, and Challenges of Modern Code Review," Proc. ICSE 2013, pp. 712–721.** Defines "Modern Code Review" (lightweight, tool-based, change-based) and empirically characterizes it at Microsoft; foundational framing for measuring review as a per-change process.
- **Shane McIntosh, Yasutaka Kamei, Bram Adams, Ahmed E. Hassan, "The Impact of Code Review Coverage and Code Review Participation on Software Quality: A Case Study of the Qt, VTK, and ITK Projects," Proc. MSR 2014, pp. 192–201** (extended: "An Empirical Study of the Impact of Modern Code Review Practices on Software Quality," Empirical Software Engineering 21(5), 2016, pp. 2146–2189). Operationalizes **review coverage** and **review participation** as component-level metrics and links them to defect-proneness — the template for a "review count / review coverage" metric, though computed at component/file level.
- **Matheus Paixão, Jens Krinke, DongGyun Han, Mark Harman, "CROP: Linking Code Reviews to Source Code Changes," Proc. MSR 2018 (Data Showcase), 4 pp.** The **Code Review Open Platform**: a curated dataset linking Gerrit reviews to *complete source snapshots* at review time (8 systems, 48,975 reviews, 112,617 patches) — solves the hard problem of connecting review events to the exact code region reviewed, enabling review-count-per-entity analyses. (Zenodo DOI 10.5281/zenodo.3599150.)
- **Georgios Gousios, Martin Pinzger, Arie van Deursen, "An Exploratory Study of the Pull-Based Software Development Model," Proc. ICSE 2014, pp. 345–355 (DOI 10.1145/2568225.2568260).** First large-scale characterization of GitHub pull requests (usage, merge rates, latency). Essential methodological grounding for treating PRs as the unit of review on GitHub.
- **Georgios Gousios, "The GHTorrent Dataset and Tool Suite," Proc. MSR 2013, pp. 233–236 (DOI 10.1109/MSR.2013.6624034; Best Data Showcase).** Scalable offline mirror of GitHub's event streams/metadata — the standard infrastructure for mining PR/review/commit linkage at scale.
- **Peter C. Rigby, Christian Bird, "Convergent Contemporary Software Peer Review Practices," Proc. ESEC/FSE 2013, pp. 202–212.** Cross-project comparison establishing that review metrics (reviewers per change, review interval, size) converge across OSS and industry — supports the validity of counting reviews per change.

*Note on granularity:* Existing review-quality work is mostly file/component-level. To count reviews at *method/class* level you will need to combine (a) a fine-grained tracker (Theme 2) to identify which methods a commit/patch touched, with (b) PR/review linkage (Gousios/GHTorrent, or Gerrit via CROP). I found no single tool that outputs "number of reviews per method" out of the box — this is a genuine gap and a contribution opportunity for your study.

### Theme 5 — Practical GitHub methodology and pitfalls

- **Eirini Kalliamvakou, Georgios Gousios, Kelly Blincoe, Leif Singer, Daniel M. German, Daniela Damian, "The Promises and Perils of Mining GitHub," Proc. MSR 2014, pp. 92–101** (extended: Empirical Software Engineering 21, 2016, pp. 2035–2071). Documents concrete perils: a repository ≠ a project; many repos are inactive/personal; and, per the abstract, "almost 40% of all pull requests do not appear as merged, even though they were." Mandatory reading for cleaning your GitHub sample and interpreting PR/merge signals.
- **git tooling.** `git log -L :<funcname>:<file>` and `git log --follow` give quick, zero-setup method/file histories but rely on git's line-based/rename heuristics (default rename similarity threshold `-M50%`) and miss moves across files, extract-method, and merge-commit changes — the exact cases where CodeShovel/CodeTracker win. `git blame` (and `-C`/`-M` options) attributes lines but does not reconstruct entity identity across refactorings.
- **Squash and rebase merges** collapse or rewrite commit history, destroying intermediate per-method revisions and detaching PR discussion from the individual changes — a critical pitfall when counting "number of revisions" or "number of reviews" on GitHub projects that squash-merge PRs. Prefer projects with merge-commit workflows, or reconstruct via the PR API rather than the mainline commit graph.
- **Rename-detection thresholds** (git's `-M`, CodeShovel's ~75% similarity, RefactoringMiner's threshold-free AST approach) materially change how many "renames" vs "delete+add" you observe, and thus entity lifespans/age. Report the tool and thresholds explicitly.
- **RefactoringMiner** (Nikolaos Tsantalis, Matin Mansouri, Laleh M. Eshkevari, Davood Mazinanian, Danny Dig, "Accurate and Efficient Refactoring Detection in Commit History," ICSE 2018, pp. 483–494; RefactoringMiner 2.0, Tsantalis, Ketkar, Dig, IEEE TSE 48(3), 2022, pp. 930–950) is the threshold-free, high-accuracy engine underpinning CodeTracker; the authors report ~98% precision / ~87% recall in the ICSE 2018 evaluation, with later versions reporting higher figures on updated benchmarks. Use it to make your tracking refactoring-aware. For non-Java: **PyRef** (Atwi et al., SCAM 2021) for Python, **RefDiff 2.0** (Silva et al.) for multi-language.

## Recommendations

**Stage 1 — Choose your tracker by language and accuracy needs.**
- If your corpus is **Java** and accuracy is paramount (age, revision counts feeding statistical models): use **CodeTracker / CodeTracker 2.0** (refactoring-aware, 99.9% precision/recall for methods). Threshold to change this choice: if runtime/scale becomes prohibitive on very large histories, fall back to **CodeShovel** (complete histories for ~90% of methods, faster, on-demand).
- If you want **git-native** artifacts you can post-process with standard git tooling: use **FinerGit** (better) or **Historage**.
- If your corpus is **polyglot**: track with **RefDiff 2.0** / language-specific detectors, and explicitly report reduced accuracy for non-Java code.

**Stage 2 — Compute modification counts as process metrics, not raw line churn.** Count fine-grained changes per method (ChangeDistiller categories), plus number-of-revisions and change entropy (Hassan), and normalize by size (relative churn, Nagappan & Ball). Benchmark: if static code metrics predict your outcome as well as process metrics, revisit feature construction (Rahman & Devanbu predict process metrics should dominate across 85 releases of 12 projects).

**Stage 3 — For review counts, build the linkage explicitly.** For GitHub PR-based projects, mine PRs via the GitHub API / GHTorrent, map each PR's changed hunks to methods using your Stage-1 tracker, and count reviews/review-comments per method. For Gerrit-based projects, use **CROP** for review-to-snapshot linkage. Compute review coverage/participation per entity following McIntosh et al.

**Stage 4 — Harden against pitfalls before drawing conclusions.** Filter non-projects/inactive repos (Kalliamvakou et al.); detect and exclude or specially handle squash/rebase-merged PRs; quantify untracked-change bias (Hora et al.) by comparing naive `git log` histories against refactoring-aware histories on a sample. Benchmark: given Hora et al.'s finding that 10–21% of method-level changes are untracked and ~25% of entities may have split histories, if your sample shows comparable discontinuity under naive tracking, refactoring-aware tracking is mandatory, not optional.

## Caveats
- **Java bias**: The most accurate trackers (CodeTracker, RefactoringMiner) and most fine-grained datasets are Java-centric. Accuracy figures (e.g., 99.9%) come from the tool authors' own oracles and may not transfer to your projects/languages; HistoryFinder (2025) explicitly questions whether inaccuracies in the CodeShovel/CodeTracker oracles propagate to tools validated against them.
- **"Review count at method level" is not directly supported by any single existing tool** — it must be assembled from a tracker plus PR/review data, and squash-merges can make it impossible to recover for some projects.
- **Some cited works are venue-dual** (e.g., Zimmermann et al. ICSE 2004 vs TSE 2005; McIntosh et al. MSR 2014 vs EMSE 2016; Kalliamvakou MSR 2014 vs EMSE 2016) — cite the version matching your needs.
- Reported accuracy/percentage figures and page numbers were cross-checked against ACM DL, IEEE, DBLP, and author pages, but a few page numbers for very recent tool papers (RAT, HistoryFinder, CodeTracker 2.0 / TSE 2024) may shift with final publication.
